# 技术手册：快捷窗缩放抖动修复 · 移植 Electron 版

> 用途：把 WPF 重写分支**已真机验证**的"快捷窗缩放抖动"修复思路，落成 Electron 版的实施方案。
> 来源：① WPF 分支的完整问题档案（见同目录《技术手册-快捷窗缩放抖动问题全集》P1~P11，含提交号）；
> ② Electron 版现状代码走查（只读，2026-10-14）。
> 前提共识（用户 2026-10-13 裁定）：**缩放中内容必须可见**——Electron 现有"缩放中内容变底色"是 WPF 已撤销的同类路线。

---

## 0. 一句话结论

把快捷窗从"**逐帧改真实窗口矩形 + CSS zoom 重排内容**"改成
"**固定画布窗（尺寸恒定，只有位置随锚点）+ 卡面合成器层 transform 缩放**"：
窗口不再逐帧变 ⇒ 系统"表面晚于矩形"的竞态从根上不存在；内容不再走布局 ⇒ 与缩放手势同帧，不再晚一拍。
主窗 / 已完成窗维持现状（WPF 同款裁定：该两窗的轻微"框先到、内容后到"用户已确认可接受）。

---

## 1. 抖动是怎么来的（Electron 现状链路）

现状链路（`HomePanel.vue` 手柄 → `store.updateUiState({clusterScale})` → 主进程
`applyClusterBounds()` → 三窗 `setBounds` → 各窗 `resize` 事件 → `zoomValue = innerHeight / 640`
→ zoom 容器重排）：

| # | 环节 | 发生了什么 | 引入的问题 |
|---|---|---|---|
| 1 | 手柄拖动 | 主窗渲染层算 scale，30ms 节流写 store | 节流量化（自家已权衡） |
| 2 | 主进程 `setBounds` | 三窗逐窗改矩形（快捷窗 = 右缘钉住、向左变宽） | **窗口矩形每帧变** |
| 3 | DWM 呈现 | 逐像素透明叠层窗的表面更新晚于矩形变更 | "框先到、内容后到"（1~2 帧错位窗） |
| 4 | 渲染层 zoom | `zoom` 是**走布局**的属性，每帧改 = 全量重排 | 内容重绘再晚一拍 |
| 5 | 双信源 | 视口反推 + 广播值混用 | 两次重排、推导差 → 呼吸式抖动（已修：单一来源） |
| 6 | 缝隙 | 三窗独立取整 | ±1px 摆动（已部分修：侧窗位置从主窗整数推导） |
| 7 | 兜底 | `clusterResizeFreeze` 缩放中侧窗内容变底色 | 拖影没了，但**缩放中看不到内容**（用户明确不要） |

**快捷窗的抖动 = 第 3 + 第 4 两层叠加**（表面竞态 × 布局延迟），第 6 层是取整相位在缝隙上的表现。
WPF 是逐层修到"固定画布"（P7）才定稿的——单修任何一层都压不住。

## 2. 修复思路（核心：让快捷窗的"框"在缩放中不动）

### 步骤 1（主笔）：快捷窗改"固定画布窗 + 卡面 transform"

**窗口侧（主进程）**

- 快捷窗尺寸恒定为**画布**：`canvasW = round(310 × maxScale)`、`canvasH = round(640 × maxScale)`；
  `maxScale` = 当前工作区下 `clampClusterScale` 的上限（**只在工作区/显示器变化时重算**，缩放手势中绝不重算）。
- 画布**右缘钉主窗左缘 − 4**（缝隙不缩放）、上缘钉锚点：
  `x = mainBounds.x − GAP − canvasW`、`y = mainBounds.y`。
- 缩放档位变化 → **画布矩形完全不动**；只有整簇拖动（锚点变化）时更新 x/y——
  位置-only 更新，不改尺寸，不触发第 3 层的表面竞态。
- `applyClusterBounds` / `showSidePanel` / 拖动快路径 / 缩进弹出 / 跨屏重申：
  **所有**摆放路径统一改用画布矩形（WPF P9 的铁律：一个窗的所有摆放路径必须用同一套矩形）。

**内容侧（快捷窗渲染层）**

- 卡面固定 `310×640`；容器 `position: absolute; top: 0; right: 0`（右上角对齐画布右上角）；
  `transform-origin: top right`；`transform: scale(k)`，`k` = 当前簇缩放值。
- **不再从视口反推 zoom**：画布恒定 ⇒ 视口恒定，反推值会永远等于上限（语义失效）。
  缩放值单一来源 = 广播的 scale；本窗对它只做一次 `transform` 赋值——无布局、无重排。
- 卡面左侧/下方的**透明画布余量**是有意为之（画布=上限档），命中处理见步骤 3。

**为什么这样就根除了抖动**

| 机制 | 消除的问题 |
|---|---|
| 快捷窗矩形恒定 | 第 3 层表面竞态（框先到内容后到）；连带 P7 的"按下/松手各闪一次"（那是两次矩形变更） |
| `transform` 不进布局 | 第 4 层（内容重排晚一拍）；即使 IPC 广播晚一帧，晚的只是一次变换赋值 |
| 缝隙 = 两条整数边之差（主窗左缘、画布右缘） | 第 6 层（缝隙随缩放变宽/变窄——WPF 的"13→17→13"不会出现） |

### 步骤 2：去掉缩放期"内容变底色"（用户可见收益）

画布方案落地后，删除快捷窗的 `clusterResizeFreeze` / `sideFrozen` 分支——缩放中内容保持可见。
这一条正是 WPF 分支撤销同类路线（"拖动期间隐藏内容只画窗壳"）的原因，也是本修复的用户可见目标之一。

### 步骤 3：透明余量的命中（不做穿透 = 吞点击）

WPF 的结论是**不要用窗口区域收窄命中**（`SetWindowRgn` 会裁剪绘制，出现"卡片缺一块"）。
Electron 有更干净的工具：

- 画布窗常驻 `setIgnoreMouseEvents(true, { forward: true })`（穿透桌面、但继续收到 mousemove）；
- 渲染层 hit-test：光标进入**卡面视觉矩形**（`getBoundingClientRect()`——transform 后的坐标已含缩放）
  → `setIgnoreMouseEvents(false)`；离开 → 恢复 `true(forward)`。
- 已知细节：penetration↔命中切换依赖"先 mousemove 后 click"的顺序，绝大多数情况没问题；
  真机验证项见 §4-5（若遇到"第一次点击被吞"，再讨论兜底）。

### 步骤 4（可选，视觉精化）：松手 settle

`transform` 缩放的是**已光栅化图层**：手势中/静止时文字可能比 `zoom` 略糊（k 越大越明显）。
若真机观感不接受，用混合方案：

- 手势中：`transform`（流畅、同帧）；
- 松手后：把卡面从 transform 切回 `zoom`（一次性重光栅化）→ 静止态像素级锐利。

先不做，真机看了再定；单独可回退。

## 3. WPF ↔ Electron 机制对照

| WPF（已验证） | Electron 对应做法 | 备注 |
|---|---|---|
| 固定画布 `QuickCanvasRect()` | BrowserWindow 尺寸=上限画布，位置=画布摆放 | **本方案核心** |
| `RenderTransform` + `RenderTransformOrigin="1,0"` | `transform: scale(k)` + `transform-origin: top right` | 不进布局、不重排 |
| `DeferWindowPos` 原子批量 | 同一 tick 内逐窗 `setBounds`（已有）；快捷窗退出逐帧改矩形后，同帧压力大减 | 快捷窗只剩位置更新 |
| `SWP_NOCOPYBITS`（作废旧像素） | **无对应 API** | 靠"窗不缩放"从根上消除，而非压制 |
| `NormalizedScale`（内容≡取整后窗口） | 主窗/已完成窗继续视口反推（已做）；快捷窗不再需要——"卡面右上角 ≡ 画布右上角"由布局保证 | 缝隙精确性由两条整数边保证 |
| 缩放角标移出缩放内容（P10） | 手柄已在主窗（无需移植） | 若未来给快捷窗加角标：必须放在 transform 层之外 |
| `SetWindowRgn` 收窄命中 ✗（会裁绘制） | `setIgnoreMouseEvents` + 渲染层 hit-test | 不要用 `setShape` / 区域收窄 |
| 物理像素 / 逻辑像素混用教训（P1） | Electron 全是 DIP（screen/win API 同一坐标系） | 别引入物理像素信源（原生插件等）；跨屏重申逻辑（#40）保留 |

## 4. 验证方法（可量化，别只看"感觉好了"）

1. **矩形恒定性**：缩放拖动时主进程逐帧打印快捷窗 `getBounds()` →
   期望 **宽高恒定、x/y 恒定**（锚点不动）。现状：宽高逐帧变。
2. **内容时机**：快捷窗渲染层确认不再监听 resize、不再改 zoom，只改 `transform`。
3. **缝隙像素**：慢放录屏逐帧量"主窗左缘 ↔ 画布右缘"的像素差 → 期望恒定
   （WPF 用同一方法取得了 13→17→13 的实证）。
4. **可见性**：缩放过程内容始终可见（不再出现底色期）。
5. **命中**：卡面外的画布余量区域，点击/拖动桌面图标应正常选中（不被吞）。
6. **清晰度**：松手后文字锐利（若明显发糊 → 上步骤 4）。

## 5. 不要走的路（Electron 版对应，均为已验证教训）

- **不要"缩放中内容变底色/隐藏"**——现状兜底；用户已否决该路线（WPF 同类方案已撤销）。
- **不要逐帧 `setBounds` 快捷窗**——这正是本方案要消除的东西（表面竞态的源头）。
- **不要用 CSS `zoom` 做逐帧手势**——走布局，必然晚于窗框。
- **不要混用缩放信源**（视口反推 vs 广播值）——自家注释已记"两次重排 = 呼吸式抖动"。
- **不要用窗口形状/区域收窄命中**——WPF `SetWindowRgn` 实测会裁剪绘制。
- **一次只改一件事、每步可单独回退**；上一步效果未确认前不叠加下一步（WPF 分支用血换来的流程纪律）。
