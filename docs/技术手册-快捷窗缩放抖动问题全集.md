# 技术实现手册：快捷窗口缩放抖动问题全集

> 定位：本分支"缩放抖动/拖影/缝隙/裁切"系列问题的**完整档案**——现象、根因、解决方案、已验证的失败路线。
> 用途：以后遇到"逐像素透明窗口（AllowsTransparency）+ 等比缩放/多窗联动"的同类需求时直接查阅。
> 全部结论来自本分支真机验证（用户肉眼判断 + 提交记录），非推测。对应提交均可在 git log 检索。
> **移植版**：把这套思路落到旧 Electron 版的实施方案，见同目录《技术手册-快捷窗缩放修复-移植Electron版.md》。

---

## 0. 背景架构（问题发生的前提）

- 三窗架构：待办主窗（设计 470×640）+ 快捷添加窗 / 已完成窗（各 310×640），全部为
  `WindowStyle=None + AllowsTransparency=True`（**逐像素透明叠层窗口**，为圆角外全透明）。
- 缩放：主窗左上角 = 锚点（不动）；快捷窗**右缘钉在主窗左缘 − 4px 缝隙**（放大=左缘左移、右缘不动）；
  已完成窗左缘钉在主窗右缘 + 4px；等比缩放，0.7 ≤ scale ≤ min(半屏高, 全宽)。
- 内容按设计尺寸（470×640 / 310×640）绘制一次，靠变换缩放，不重排版面。

**根本矛盾（本系列所有问题的源头）**：
`AllowsTransparency` 的叠层窗口在**窗口矩形变化**时，DWM 会先把**上一帧的旧表面**按新矩形
重贴/拉伸顶上，应用随后才送来新表面——"框（矩形）先到、内容（表面）后到"，中间存在 1~2 帧
的错位窗口期。任何"每帧改矩形"的窗口都会有这个错位，只是内容越复杂越显眼。

## 1. 问题清单与解决方案（按因果链排序）

### P1 拖动越拖越偏（鼠标与窗口分离）
- **现象**：拖动标题栏，窗口比鼠标"跑得快"，越拖偏得越多。
- **根因**：`PointToScreen` 返回**物理像素**，`Window.Left/Top` 是**逻辑像素（DIP）**；
  125% DPI 下直接混用，每帧多算 25%。
- **解**：采样后统一除以 `VisualTreeHelper.GetDpi().DpiScaleX/Y` 再进锚点运算。（`9666c32`）

### P2 缩放时"往右弹一下再回来"（先宽度后位置的两笔写入）
- **现象**：快捷窗（右缘钉住）缩放瞬间先向右弹一格再回位。
- **根因**：WPF 的 `Left/Width` 是两个独立属性、各自触发一次 `SetWindowPos`。
  先写宽度后写位置 → 出现"已是新宽度、仍在旧位置"的真实中间态，合成器把它画了出来。
- **解**：**原子定位**——`SetWindowPos` 一次提交 (x, y, cx, cy)；
  三窗再升级为 `BeginDeferWindowPos/DeferWindowPos/EndDeferWindowPos` 同批提交，
  避免逐窗提交之间被插入一次呈现（同帧内三窗不同步）。（`1767931` → `79bda88`）

### P3 高 DPI 亚像素抖动（±1px 呼吸）
- **现象**：缩放中边缘/缝隙有 ±1px 的宽度波动。
- **根因**：逻辑像素坐标 ×1.25 后是小数，各边各自取整 → 同一条边逐帧落在不同物理像素上。
- **解**：①锚点对齐整数物理像素后再派生三窗几何（`SnappedAnchor`）；
  ②摆放时**两条边各自取整、宽高=两边相减**，"钉住的边"逐帧精确落在同一物理像素。（`3ee1abb`）

### P4 重绘前错位（系统按左上角搬移旧内容）
- **现象**：右缘钉住、向左变宽的窗口，重绘前一帧右缘像"先缩再弹"。
- **根因**：`SetWindowPos` 默认把旧客户区像素按**左上角**对齐搬移——与"右缘钉住、向左伸展"
  的锚定方向相反。
- **解**：加 `SWP_NOCOPYBITS`（整块作废旧像素、当帧重画）。（`7741e53`）

### P5 逐帧写 WPF 窗口几何属性造成额外中间态
- **根因**：逐帧同时写 `Left/Top/Width/Height` 会发出多次非原子 `SetWindowPos`，
  把"新位置+旧尺寸"的中间态更多地暴露给合成器。
- **解**：**逐帧路径上不写 WPF 窗口几何属性**，只走原子批量；WPF 自己跟随 WM_SIZE 同步属性。
  （`22d5b2d`，注释已固化在 `PlaceBatch`）

### P6 内容宽度与窗口宽度差零点几像素 → 缝隙变宽/右缘被裁
- **现象**（用户视频慢放实证）：缩放中缝隙 13→17→13（视频像素）。
- **根因**：窗口宽度要落到整数物理像素（`round(rect×sx)`），而内容若按**未取整的 scale** 排版，
  两者差零点几像素：内容窄于窗口 ⇒ 卡面右缘缩进窗内（缝隙"变宽"）；宽于 ⇒ 被裁一条。
  实测该偏差随档位漂移约 0.4 设计单位。
- **解**：**内容缩放比从"窗口取整后的实际宽度"反推**（`NormalizedScale(矩形宽, 设计宽)`），
  使内容布局尺寸 ≡ 客户区尺寸。实测偏差 0.4 → 0.03 设计单位。（`8544a9b`）

### P7 按下/松开缩放柄各闪一次 + 缩放中残影（固定画布方案的由来）
- **现象**：按下角标瞬间、松开瞬间各闪一次；拖动中右缘有拖影。
- **根因**：这两次闪动是"按下预放大/松手收回"两次**矩形变更**；拖动中残影是"逐帧改矩形"本身
  （见 §0 根本矛盾）。
- **解（最终形态，快捷窗专用）**：**固定画布**——
  1. 窗口矩形恒定 = `max(设计尺寸, 设计尺寸×缩放上限)`（`QuickCanvasRect()`），
     右缘仍钉主窗左缘−缝隙、上缘钉锚点；**按下/拖动/松手全程零矩形变更**；
  2. 卡面 = 固定设计尺寸 310×640（底色+描边+内容整体），右上角对齐，
     **渲染层 `ScaleTransform`（`RenderTransformOrigin=1,0`）**表现大小 → 右缘钉死、向左下缩放；
  3. `ApplyLayout` 与 `MoveCluster`（移动快路径）**都**摆画布矩形——两条路径必须一致，
     否则"移动中被裁、松手恢复"（P9）。
  代价：卡面外一圈透明画布余量（下限档时约 60×128 设计单位），该区域**会吞掉点击**。
  （`9c18601` → `2254491` → `5d0128c` → `b2716ea`）

### P8 一按角标整块卡"跳成最大"
- **根因**：P7 预放大画布后，卡面若仍铺满窗口，就会跟着撑到上限。
- **解**：卡面尺寸与窗口解耦（固定设计尺寸、右上角对齐、渲染层缩放），见 P7。(2254491)

### P9 移动过程中被裁、松手恢复
- **根因**：移动快路径 `MoveCluster` 仍用**目标矩形**摆快捷窗（217 宽），而缩放/松手路径
  （`ApplyLayout`）用**画布矩形**（310 宽）——两条路径不一致。
- **解**：`MoveCluster` 里快捷窗同样用 `QuickCanvasRect()`。**规则：一个窗的所有摆放路径
  必须用同一套矩形。**（`b2716ea`）

### P10 缩放角标相对边框跑位
- **根因**：角标位于**被缩放的 CardContent 内部**（设计坐标右下角），随"内容重排晚一拍"一起滞后。
- **解**：角标**移出缩放内容**，钉在窗口右下角（布局上不受内容缩放影响，位置恒定）；
  自身大小用渲染层 `ScaleTransform`（锚点右下角）随档位变化。（`ffdb5fa`）

### P11 启动闪一下巨窗（1536×844）
- **根因**：先 `Show()` 后摆位，显示瞬间是 WPF 默认尺寸。
- **解**：未显示窗口先同步 WPF 属性再 `Show()`（一次落位）；已显示窗口走原子批量。（`4b2522f`）

## 2. 已验证的**失败/高风险路线**（不要重蹈）

| 路线 | 为什么失败 |
|---|---|
| **方案 B**：窗口矩形照旧逐帧变、内容改渲染层缩放 | 内容在布局上仍是设计尺寸，**溢出窗口被裁**/与卡片对不上——"内容填满卡片"必须由布局保证；渲染层缩放救不了"框已变、内容是按设计尺寸画的"这一事实。（`7cc4805` → `f0ab731` 回滚） |
| **窗口区域 `SetWindowRgn` 收窄命中** | 区域**会裁剪绘制**：尺寸一旦算错（或表面更新晚于位置）就把卡片裁掉一块（"缺一块/内容切半截"）。且 `WindowFromPoint` 对叠层窗口疑似不按区域判定，穿透效果还不确定。**结论：不要用区域做穿透/命中收窄。**（`21a1ad4`→`bd378bc`→`f89f2a4` 移除） |
| **拖动期间隐藏内容只画窗壳** | 用户明确不要（拖动中看不到文字）；且"慢"的根源是通道差异，不是像素量。（`92413ee` 已撤销） |
| **LayoutTransform 与 RenderTransform 混用不清后果** | 两者对"内容是否参与布局"语义完全不同：Layout=内容参与布局、与客户区耦合（填满有保证）；Render=内容按设计尺寸画、与客户区脱钩（会溢出/裁切）。**同一个窗内两者不可随意互换。** |
| **逐窗 SetWindowPos / 先宽度后位置** | 见 P2（两笔写入的中间态）。 |
| **在"未回退、效果未确认"的改动上继续叠加** | 流程教训（用户裁定，已写入 AGENTS.md/需求文档/开场白）：用户说"没效果"→ 先干净回退，再谈下一步。 |

## 3. 最终形态（当前版，`ffdb5fa`）

| 窗 | 窗口矩形 | 内容缩放 | 命中 |
|---|---|---|---|
| 待办主窗 | 目标矩形逐帧变（左上角=锚点） | LayoutTransform，比例=NormalizedScale | 整窗即卡面 |
| 已完成窗 | 目标矩形逐帧变（左缘随主窗右缘平移） | LayoutTransform，比例=NormalizedScale | 整窗即卡面 |
| 快捷添加窗 | **固定画布**（右缘钉主窗左缘−4、上缘钉锚点，尺寸=上限档） | **卡面渲染层 ScaleTransform（锚点右上角）** | 整窗（含透明余量，会吞点击） |

配套不变量（改动时必须保持）：
1. 快捷窗的**所有**摆放路径（ApplyLayout / MoveCluster / 未来新增）都用 `QuickCanvasRect()`；
2. 三窗的钉住关系：主窗左上角=锚点；快捷窗右缘=锚点−4；已完成窗左缘=锚点+主宽+4；
3. 所有矩形提交走 `WindowPlacement.SetBoundsBatch`（原子+取整+NOCOPYBITS）；
4. 内容缩放比例一律 `NormalizedScale`（从取整后的窗口宽度反推），不要直接用原始 scale。

## 4. 快速诊断表（下次遇到先对号）

| 症状 | 先查 | 对应章节 |
|---|---|---|
| 拖动越拖越偏 | DPI 换算（物理 vs 逻辑） | P1 |
| 缩放瞬间"弹一下再回位" | 是否原子提交；是否逐帧写 Left/Width | P2 / P5 |
| 边缘 ±1px 呼吸 | 物理像素取整方式（两边相减） | P3 |
| 重绘前一帧错位 | SWP_NOCOPYBITS | P4 |
| 缝隙随缩放变宽/变窄 | 内容缩放比是否 NormalizedScale | P6 |
| 按下/松手闪动、拖动中拖影 | 该窗是否固定画布 | P7 |
| 一按就跳成最大 | 卡面是否与窗口解耦 | P8 |
| 移动中被裁、松手恢复 | 各摆放路径矩形是否一致 | P9 |
| 角标相对边框跑位 | 角标是否在缩放内容里 | P10 |
| 启动闪巨窗 | 先摆位后 Show | P11 |
| 内容被裁/与卡片分离 | RenderTransform 窗口是否比内容窄（方案 B 陷阱） | §2 |

## 5. 残留已知代价（记录在案）

- 快捷窗透明画布余量会吞点击（不做穿透）。缓解方向（未实施）：让画布尺寸恒等于当前档卡面、
  仅在按下角标时临时放大画布——但那会重新引入两次矩形变更（= 按下/松手闪动），需要权衡；
  或改用 `WM_NCHITTEST` 返回 `HTTRANSPARENT` 的做法（未验证）。
- 主窗/已完成窗仍是"逐帧改矩形"老路，其自由边在拖动中仍可见轻微"框先到、内容后到"
  （用户确认可接受）。若要根除，需对这两窗也上固定画布（已完成窗要额外渲染层平移），
  实验态见标签 `回退前-1f84d8e`。
